   it relates to your own work.

## Break on Through to the Other Side: Pooling Memory Elastically with RamRyder
{: #RamRyder}

*Yanbo Zhou and Steven Swanson (UC San Diego), with Shanghai Jiao Tong University and Samsung Semiconductor* · [Paper](https://www.usenix.org/system/files/osdi26-zhou-yanbo.pdf) · [Code](https://github.com/ramryder-project/ramryder)
{: .paper-meta}

- CXL
- Memory tiering
- Virtualization
{: .paper-tags}

**In one sentence.**

Memory bandwidth should be allocated as a cloud resource in its own right, just like CPU and memory capacity.

**Background.**

- Memory allocation in the cloud is not flexible enough: vendors allocate memory capacity in a fixed ratio to vCPUs and offer no way to allocate bandwidth. The authors' analysis of Alibaba's cluster traces shows that 90% of servers exhibit average bandwidth utilization below 44.5%.
- Underutilized bandwidth is not necessarily correlated with underutilized capacity, because they exhibit different spatial and temporal patterns.

**Approach.**

- RamRyder is a software-defined elastic memory system for cloud VMs that adjusts capacity and bandwidth dynamically, by managing memory at channel granularity.
- Components:
   - Host user space resource manager: channel allocation
   - Hypervisor: virtualize memory channels
   - Modified guest kernel: page-to-channel allocation policies

**Evaluation.**

- Implemented on unmodified commodity servers
   - Disable existing DIMM channel interleaving via BIOS/UEFI
   - CXL devices reserved as a separate DAX device in user space with CXL configuration tools
- Test setup:
   - AMD EPYC Zen 5 with 12 DDR5 channels per socket; each VM's vCPUs are pinned to their own CCXs, so VMs do not share an L3 cache
   - 8 of the 12 channels in one socket are used, each populated with one 32 GB DDR5 DIMM, to match compute-optimized cloud instances
   - 4 × 256 GB Samsung CXL 2.0 memory devices
   - Debian with Linux 6.15
- RamRyder improves average capacity and bandwidth utilization by 28.6% and 43.2%, respectively, across the cluster while delivering performance comparable to the best case with exclusive access

**Food for thought.**

- Limitations: the mapping from physical addresses to memory channels is normally hidden from system software, so deployment means turning off channel interleaving in BIOS/UEFI (a boot-time setting), and the guest kernel must be modified

## Finding NEMO: Nimble and Expressive Memory Observability
{: #NEMO}

*Shihang Li, Matthew Giordano and Simon Peter (University of Washington), with Meta and Microsoft Azure* · [Paper](https://www.usenix.org/system/files/osdi26-li-shihang.pdf) · [Code](https://github.com/vic-lsh/nemo)
{: .paper-meta}

- CXL
- Memory tiering
{: .paper-tags}

**In one sentence.**

A small, programmable telemetry engine in the memory controller lets the OS count exactly the memory accesses it cares about, at the granularity it chooses, without spending CPU time.

**Background.**

- A long-standing need for easy and efficient hardware and software mechanisms that can track memory usage on multi-tier memory systems.
- Existing mechanisms:
   - page level access bit tracking, expensive
   - hardware cache miss sampling, reduced precision (HeMem)

**Approach.**

- NEMO, a hardware-software codesigned memory telemetry engine
   - On the hardware side, NEMO is a lightweight extension to memory controllers (MCs)
   - On the software side, NEMO exposes an OS-facing programming model and Linux driver
- MCs already host QoS and monitoring features; the NEMO pipeline runs alongside, rather than on, the memory datapath.
- To support different granularities of monitoring (cache line to multi-GiB regions), the "match stage" masks and shifts the request's physical address with OS-set parameters (simple fixed-latency arithmetic, not a hash) and looks the result up in a small translation table to find the counter. For page-hotness tracking, a 2 MiB page granularity is adopted

**Evaluation.**

- Altera Agilex 7 FPGA I-Series Development Kit with CXL 2.0 Type-3 support in hard IP
- SRAM per NEMO pipeline: ~150 KiB
- Across the full bitstream, NEMO uses 4.4% of the FPGA’s M20K SRAM and 4.8% of its logic
- Speeds up HeMem’s reaction to hot-set changes by 5×, accelerates THP splitting in MEMTIS by 10.4×, and detects noisy neighbors in Linux with 350× lower overhead. These telemetry improvements yield up to 1.7× higher throughput and 23% lower latency across key-value stores and databases

**Food for thought.**

This paper overlaps a lot with my past work.

- One data point from my own experience: scanning the page table (test-and-clear of the accessed bits) for 1 GB of address space (one VMA of 4 KiB pages, memset first so that every PTE really exists) takes about 1 ms, so 1 TB would take about 1 s, long enough for the accessed bits to go stale. And as the authors point out, one bit per page is too coarse-grained.
- 2 MiB granularity is a common, wise and practical choice for page temperature tracking.
- The memory controller is a compelling place for hardware event monitoring. The prototype already sits in a CXL memory expander's controller; I would imagine future CXL devices shipping such engines to hint the OS and other system software.
