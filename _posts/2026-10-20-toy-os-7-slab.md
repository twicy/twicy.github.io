# Toy OS 7: Slab and kmalloc

*Toy OS worklog: [1. Real mode](/blogs/os/toy-os-1-real-mode.html) · [2. Segmentation](/blogs/os/toy-os-2-segmentation.html) · [3. Paging](/blogs/os/toy-os-3-paging.html) · [4. Kernel](/blogs/os/toy-os-4-kernel.html) · [5. Interrupts](/blogs/os/toy-os-5-interrupts.html) · [6. Buddy](/blogs/os/toy-os-6-buddy.html) · **7. Slab** · [Source](https://github.com/twicy/toy-os/tree/fc88a1de36e8cd2cf495c46f3e6b36c01fc94f8b)*

The buddy allocator (post 6) hands out 4 KiB at a time, but a list node, a cache descriptor or a small buffer is a few dozen bytes. A *slab allocator* sits on top of it. It takes whole pages, cuts each into equal-size objects, and keeps one cache per object size. This post covers the slab layer ([`442dcfe`](https://github.com/twicy/toy-os/commit/442dcfe)) and `kmalloc`/`kfree` on top of it ([`fc88a1d`](https://github.com/twicy/toy-os/commit/fc88a1d)), the last commit of this series.

ULK (ch. 8, "Memory Area Management") describes Linux's original SLAB allocator. It has cache descriptors, separate slab descriptors, per-object descriptor arrays, coloring and per-CPU caches, after Bonwick's design for Solaris. toy-os is much smaller, and in two ways it is closer to SLUB, which replaced SLAB as Linux's default: the slab's bookkeeping lives in its `struct page`, and a free object itself holds the pointer to the next free object.

## One struct page, three owners

The slab commit adds three fields to `struct page` and one flag:

```c
#define PG_reserved (1u << 0)
/* Set if it is the first page of a free block in buddy system */
#define PG_buddy (1u << 1)
/* Set on every page that is a slab, the slab fields below are valid */
#define PG_slab (1u << 2)
/* Set on the first page of a kmalloc too large for a slab, order holds its size */
#define PG_large (1u << 3)

struct page {
    uint16_t flags;
    uint16_t order;
    int32_t refcount;
    /* buddy: the free list of its order, slab: the partial list of its cache */
    struct list_head lru;
    /* PG_slab only, a slab is exactly one page so these describe the whole slab */
    struct kmem_cache *slab_cache;
    void *freelist;                 /* first free object, NULL when the slab is full */
    uint32_t inuse;                 /* objects handed out, 0 is empty, cache->objects is full */
};
```

![Which struct page fields each owner uses: a free buddy block uses flags, order and lru; a slab page uses flags, refcount, lru, slab_cache, freelist and inuse; a large kmalloc uses flags, order and refcount](/assets/images/posts/toy-os-7-slab/struct-page.svg)

*The 28 bytes of `struct page` and who uses which field.*

As my commit note says, `lru` is "shared" by the buddy and slab layers. A page cannot be free in the buddy system and hold objects in a slab at the same time, so the same `list_head` links free blocks in post 6 and partial slabs here. Linux's `struct page` takes this much further, with unions of fields for every possible owner.

## Caches and slabs

A cache is little more than a size and a list:

```c
/* Example: struct kmem_cache "kmalloc-1024"
 * size = 1024, objects = 4
 * partial is a linked list whose container is struct page
 */
struct kmem_cache {
    const char *name;
    uint32_t size;
    uint32_t objects;
    /* Non-full slabs, slab = page frame here */
    struct list_head partial;
};

void kmem_cache_init(struct kmem_cache *cache, const char *name, uint32_t size, uint32_t align) {
    if (align == 0)
        align = sizeof(void *);
    ASSERT(is_pow2(align));
    ASSERT(size <= PAGE_SIZE && align <= PAGE_SIZE);

    size = ALIGN_UP(MAX(size, sizeof(void *)), align);

    cache->name = name;
    cache->size = size;
    cache->objects = PAGE_SIZE / size;
    INIT_LIST_HEAD(&cache->partial);
}
```

A slab is exactly one page. Every object is at least pointer-sized, because a free object stores the pointer to the next free object in its first 4 bytes. `new_slab` takes a page from the buddy system and threads that list through it. It walks backwards, so the list starts at object 0 and runs in address order:

```c
/* Carve a fresh page */
static struct page *new_slab(struct kmem_cache *cache) {
    struct page *page = alloc_pages(0);
    char *base;

    if (!page)
        return NULL;

    base = page_address(page);
    page->freelist = NULL;
    /* Each slot either holds a valid obj or pointer to the next slot */
    /* As long as the slab is "partial", it's freelist is bound to point to a
     * free slot which should further point to its next free slot if possible
     */
    for (uint32_t i = cache->objects; i > 0; i--) {
        void **obj = (void **)(base + (i - 1) * cache->size);
        *obj = page->freelist;
        page->freelist = obj;
    }
    page->flags |= PG_slab;
    page->slab_cache = cache;
    page->inuse = 0;
    list_add(&page->lru, &cache->partial);
    return page;
}
```

The list costs no memory: free objects are unused memory anyway. Once objects are allocated and freed in random order, it no longer runs in address order:

![A kmalloc-512 slab with slots 0, 2, 3 in use: struct page freelist points to slot 1, then 4, 5, 6, 7, then NULL](/assets/images/posts/toy-os-7-slab/slab-page.svg)

*One slab after four allocations and one free. The free list is a stack (LIFO).*

## Allocating and freeing objects

```c
void *kmem_cache_alloc(struct kmem_cache *cache) {
    struct page *page;
    void **obj;

    if (list_empty(&cache->partial) && !new_slab(cache))
        return NULL;

    /* pop the head of the first partial slab's free list */
    page = list_first_entry(&cache->partial, struct page, lru);
    obj = page->freelist;
    page->freelist = *obj;
    page->inuse++;

    /* a full slab leaves the partial list, kmem_cache_free puts it back */
    if (page->inuse == cache->objects)
        /* Do not worry about losing track of full slabs, see kmem_cache_free() */
        list_del_init(&page->lru);
    return obj;
}
```

The cache tracks only *partial* slabs, the ones with at least one free object, so allocation never has to search. A full slab simply drops off the list. Nothing needs to find it until one of its objects is freed, and then the object's address leads straight back to it: `virt_to_page(obj)` gives the page, and the page gives its cache.

```c
void kmem_cache_free(struct kmem_cache *cache, void *obj) {
    struct page *page = obj_to_page(obj);

    ASSERT((page->flags & PG_slab) && page->slab_cache == cache);
    /* must be the start of an object, not a pointer into the middle of one */
    ASSERT(((uintptr_t)obj - (uintptr_t)page_address(page)) % cache->size == 0);
    /* a cheap double free check, it only catches freeing the last freed object again */
    ASSERT(page->inuse > 0 && obj != page->freelist);

    /* a full slab is about to have a free object, so it can serve allocations again */
    if (page->inuse == cache->objects)
        list_add(&page->lru, &cache->partial);

    /* push onto the free list */
    *(void **)obj = page->freelist;
    page->freelist = obj;
    page->inuse--;

    /* keep one slab even when empty, so allocating and freeing a single
     * object in a loop does not go to the buddy system every time */
    if (page->inuse == 0 && !list_is_singular(&cache->partial))
        free_slab(page);
}
```

Empty slabs go back to the buddy system (`free_slab` clears `PG_slab`, then calls `free_pages`). The exception is a cache's last slab. Without that exception, a loop of `kmalloc(32)`/`kfree` would split and merge a buddy block on every iteration.

## kmalloc and kfree

`kmalloc` picks one of nine caches, `kmalloc-8` to `kmalloc-2048`, by rounding the size up to a power of two. Anything bigger goes straight to the buddy allocator:

```c
/* index of the smallest kmalloc cache holding size bytes, 0 < size <= KMALLOC_MAX_CACHE_SIZE */
static inline uint32_t kmalloc_index(uint32_t size) {
    if (size <= (1u << KMALLOC_MIN_SHIFT))
        return 0;
    /* 32 - clz(size - 1) is log2 of size rounded up to a power of 2 */
    return 32 - __builtin_clz(size - 1) - KMALLOC_MIN_SHIFT;
}

void *kmalloc(size_t size) {
    struct page *page;
    uint32_t order;

    if (size == 0 || size > KMALLOC_MAX_SIZE)
        return NULL;
    if (size <= KMALLOC_MAX_CACHE_SIZE)
        return kmem_cache_alloc(&kmalloc_caches[kmalloc_index(size)]);

    /* too large for a slab: a buddy block of its own, its first page
     * remembers the order so kfree knows how much to give back */
    order = get_order(size);
    page = alloc_pages(order);
    if (!page)
        return NULL;
    page->flags |= PG_large;
    page->order = order;
    return page_address(page);
}
```

| `size` (bytes) | Comes from | Objects per page |
| --- | --- | --- |
| 1 – 8 | `kmalloc-8` | 512 |
| 9 – 16 | `kmalloc-16` | 256 |
| 17 – 32 | `kmalloc-32` | 128 |
| 33 – 64 | `kmalloc-64` | 64 |
| 65 – 128 | `kmalloc-128` | 32 |
| 129 – 256 | `kmalloc-256` | 16 |
| 257 – 512 | `kmalloc-512` | 8 |
| 513 – 1024 | `kmalloc-1024` | 4 |
| 1025 – 2048 | `kmalloc-2048` | 2 |
| 2049 – 4 MiB | `alloc_pages(get_order(size))`, marked `PG_large` | |
| 0, or more than 4 MiB | `NULL` | |

There is no `kmalloc-4096`. A 4 KiB object would fill a whole page, and a page is what the buddy allocator already hands out. A size of 2049 bytes still costs a whole page, which is the price of power-of-two classes. Every object is aligned to its size (up to `PAGE_SIZE`), since a slab starts on a page boundary and objects are packed at multiples of the size.

`kfree` gets only a pointer. The page's flags say where it came from, and that is the point of `PG_large`. As my commit note says, it is cheap and lets `kmalloc` and `kfree` pair up:

```c
void kfree(const void *ptr) {
    struct page *page;
    uint32_t order;

    if (!ptr)
        return;

    /* the page says which kind of kmalloc it was */
    page = obj_to_page(ptr);
    if (page->flags & PG_slab) {
        kmem_cache_free(page->slab_cache, (void *)ptr);
        return;
    }

    ASSERT((page->flags & PG_large) && ptr == page_address(page));
    order = page->order;
    page->flags &= ~PG_large;
    page->order = 0;
    free_pages(page, order);
}
```

![kmalloc routes sizes up to 2048 through kmalloc_index to one of nine caches, each with a partial list of slab pages; larger sizes go to alloc_pages with PG_large; kfree looks at the page flags to choose the path back](/assets/images/posts/toy-os-7-slab/kmalloc-flow.svg)

*The two paths through `kmalloc`, and how `kfree` finds the right one.*

The checks catch a lot: a pointer below `0xC0000000` or beyond RAM, a pointer into the middle of an object, a page that is neither a slab nor a large allocation, and freeing the same object twice in a row. My commit note also records what they miss. A wrong pointer that happens to land on the start of *another* object passes every check, and that object is freed while someone still uses it. Linux catches that class of bug with KASAN, which keeps shadow memory to track whether each byte may be accessed.

`kmem_cache_create()` makes a cache for a specific object type. The `struct kmem_cache` itself (20 bytes) comes from `kmalloc`, in this case from `kmalloc-32`.

## Watching it work

`main()` at [`fc88a1d`](https://github.com/twicy/toy-os/commit/fc88a1d) only calls `init_kmalloc()`. To see the allocator at work, add a throwaway test after it (it is not part of the commit):

```c
static void kmalloc_demo(void) {
    char *a = kmalloc(24);
    char *b = kmalloc(24);
    char *c = kmalloc(100);
    char *big = kmalloc(5000);

    printk("kmalloc(24)   = %p\n", a);
    printk("kmalloc(24)   = %p\n", b);
    printk("kmalloc(100)  = %p\n", c);
    printk("kmalloc(5000) = %p\n", big);
    kfree(b);
    printk("kfree(%p), then kmalloc(20) = %p\n", b, kmalloc(20));
}
```

![Bochs: kmalloc(24) = 0xc0500000, kmalloc(24) = 0xc0500020, kmalloc(100) = 0xc0582000, kmalloc(5000) = 0xc0584000, kfree(0xc0500020), then kmalloc(20) = 0xc0500020](/assets/images/posts/toy-os-7-slab/kmalloc-demo.png)

*The test's output. Every address can be predicted from the free lists in post 6.*

1. **`kmalloc(24)`** rounds up to `kmalloc-32`, which has no slab yet. `new_slab` asks for an order-0 page, and the order-0 list holds exactly one: pfn `0x500`, the page left over from the loader's tables. Object 0 is at `0xC0500000`.
2. **`kmalloc(24)` again** pops object 1 from the same slab, 32 bytes later: `0xC0500020`.
3. **`kmalloc(100)`** goes to `kmalloc-128`, which needs a new slab. The order-0 list is now empty, so the buddy allocator splits the order-1 block at `0x582`. It returns `0x582` and puts `0x583` on the order-0 list. Result: `0xC0582000`.
4. **`kmalloc(5000)`** is too big for a slab: `get_order(5000)` = 1, two pages. The order-1 list is empty after step 3, so the order-2 block at `0x584` splits into `0x584` (returned) and `0x586` (back on the order-1 list). That is the split pictured in post 6. Result: `0xC0584000`, with `PG_large` and `order = 1` on its first page.
5. **`kfree(b)` then `kmalloc(20)`**: `b` goes back on the head of its slab's free list, and the next `kmalloc-32` allocation gets it right back, `0xC0500020`. The most recently freed object is the most likely to still be in the CPU cache.

All of these are direct-map addresses: physical = virtual − `0xC0000000`, and each allocation is physically contiguous. That is what DMA buffers and page tables need, but it is also the weakness of `kmalloc`. Once physical memory fragments, a large `kmalloc` fails even when there is plenty of free memory in total.
